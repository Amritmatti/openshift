# Employee directory sample app

This is a three-tier Node.js sample for storing employee records: ID (generated by PostgreSQL), name, email, date of birth, location, department, and job title. It is deliberately split into the requested project directories:

| Directory / OpenShift project | Responsibility | Publicly exposed? |
| --- | --- | --- |
| `frontend/` / `frontend` | Node/Express UI server and browser application | Yes, through `employee-ui` Route |
| `backend/` / `backend` | Node/Express REST API and validation | No |
| `db/` / `db` | PostgreSQL schema and durable data | No |

The browser calls `/api` on the frontend. The frontend server proxies it to the backend, which is the only component that uses database credentials. The `frontend` NetworkPolicy is additionally permitted to reach both `backend` and `db`, as requested, but no DB credentials are placed in the frontend image or environment. This preserves the requested network path without exposing the database password to a browser-facing workload.

## Run locally with persistent data

Docker Compose builds all three containers and creates the named volume `employee-db-data`. Start it from the repository root:

```bash
docker compose up --build -d
docker compose ps
curl -fsS http://localhost:8080/healthz
```

Open <http://localhost:8080>, enter an employee, then stop and start the stack. `down` without `-v` and `stop` retain the PostgreSQL volume:

```bash
docker compose stop
docker compose start
# Or: docker compose down && docker compose up -d
```

Verify the saved employee is still returned:

```bash
curl -fsS http://localhost:8080/api/employees
```

Only run the following command when intentionally deleting all employee data:

```bash
docker compose down -v
```

## API

The frontend proxies these endpoints to the private backend service:

```text
GET    /api/employees
POST   /api/employees
DELETE /api/employees/:id
GET    /healthz
```

Example create request:

```bash
curl -X POST http://localhost:8080/api/employees \
  -H 'content-type: application/json' \
  -d '{"name":"Ada Lovelace","email":"ada@example.test","dateOfBirth":"1815-12-10","location":"London","department":"Engineering","jobTitle":"Programmer"}'
```

Email is unique; required fields and basic email/date formats are validated by the backend. The database initializes its schema from `db/init/001-schema.sql` only when its data directory is first created.

## Deploy to OpenShift

`manifests/employee-app/openshift.yaml` creates three namespaces (projects), services, a durable database PVC, workload templates, a frontend Route, and namespace-based network policies. It expects images you have built and pushed to a registry that your cluster can pull from.

1. Build and push the three images. For example, replace `REGISTRY/ACCOUNT` with your approved registry path:

   ```bash
   docker build -t REGISTRY/ACCOUNT/employee-frontend:latest frontend
   docker build -t REGISTRY/ACCOUNT/employee-backend:latest backend
   docker build -t REGISTRY/ACCOUNT/employee-db:latest db
   docker push REGISTRY/ACCOUNT/employee-frontend:latest
   docker push REGISTRY/ACCOUNT/employee-backend:latest
   docker push REGISTRY/ACCOUNT/employee-db:latest
   ```

2. Edit the manifest before applying:
   - replace every `quay.io/REPLACE_ME/...` image reference;
   - replace both `replace-before-applying` password values with the **same strong password**;
   - if the cluster does not provide a default StorageClass, set an approved `storageClassName` on `employee-db-data`.

3. Apply and wait:

   ```bash
   oc apply -f manifests/employee-app/openshift.yaml
   oc -n db wait --for=condition=Ready pod -l app.kubernetes.io/component=db --timeout=5m
   oc -n backend wait --for=condition=Ready pod -l app.kubernetes.io/component=backend --timeout=5m
   oc -n frontend wait --for=condition=Ready pod -l app.kubernetes.io/component=frontend --timeout=5m
   oc -n frontend get route employee-ui
   ```

4. Browse to the Route host:

   ```bash
   printf 'https://%s\n' "$(oc -n frontend get route employee-ui -o jsonpath='{.spec.host}')"
   ```

### Connectivity controls

The policies use namespace labels installed by the manifest. They restrict egress and backend/database ingress as follows:

```text
frontend -> backend, db, DNS
backend  -> db, DNS
 db      -> (no egress)
```

Database ingress is permitted from `frontend` and `backend`, while the backend accepts ingress only from `frontend`. The database has an empty egress list, so it cannot initiate connections to either other project. NetworkPolicy enforcement requires an OpenShift network plugin that enforces Kubernetes `NetworkPolicy` objects.

## Persistence and operations

The PostgreSQL deployment mounts the `db/employee-db-data` PVC at `/var/lib/postgresql/data`. Restarting or deleting the database **pod/container** does not remove records; Kubernetes reattaches the same claim. Do not delete `employee-db-data` if you need the data. To inspect it after deployment:

```bash
oc -n db get pvc employee-db-data
oc -n db logs deployment/employee-db
oc -n backend logs deployment/employee-api
```

For production, use registry-pinned image digests, a managed/high-availability database or tested backup and restore plan, external secret management, TLS for database connections, resource requests/limits, and an OpenShift-compatible PostgreSQL image verified under the restricted SCC.
